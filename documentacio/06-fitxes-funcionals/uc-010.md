# Fitxa funcional — UC-010 — Gestionar configuració i versió del SIF

**Versió de la fitxa:** 2.0  
**Data d'auditoria:** 2026-10-03  
**Estat documental:** `AUDITED_CASE_SPECIFIC`  
**Estat d'implementació:** `IMPLEMENTED_ON_BRANCH_PENDING_CI_AND_ENV_EVIDENCE`  
**Branca:** `audit/uc-010-governanca-versio-2026-10-03`  
**PR:** #139  
**Domini:** governança, desplegament, configuració i evidència operativa.

## 1. Objectiu

Registrar de forma auditable quina versió del SIF està **realment desplegada i observada**, vincular-la amb:

- commit declarat de runtime;
- hash dels bytes físics del release;
- hash de configuració efectiva;
- versió/esquema de base de dades;
- declaració responsable aprovada i document físic;
- evidència de backup/restauració quan la política ho exigeix;

i serialitzar la decisió d'activació sense confondre “desplegar”, “tenir una fila SQL” o “tenir una branca Git” amb “versió activa verificada”.

## 2. Actors

| Actor | Permís |
| --- | --- |
| Responsable tècnica / administració SIF | consulta + alta candidata + declaració + preflight + activació |
| Direcció/aprovador autoritzat | entra al mateix circuit amb rol manage quan ha d'aprovar la declaració |
| Auditor / consulta | lectura de runtime, candidates, declaracions i journal |
| Sistema SIF | verifica bytes/config/esquema, aplica locks i escriu evidència |

Els rols són configurables i **no tenen defaults permissius**.

## 3. Canals

### Canal principal

Intranet PrisMa → launch HMAC signat → `pay.prisma.cat/sif/versions/`.

### Canal tècnic

CLI:

- `sif/scripts/build-release-manifest.php`;
- `sif/scripts/preflight-version-governance.php`.

No existeix una ruta pública que permeti activar una versió sense sessió/rol/CSRF.

## 4. Preconditions

Per consultar:

1. actor autenticat per launch HMAC anti-replay;
2. rol en `SIF_VERSION_READ_ROLES` o `SIF_VERSION_MANAGE_ROLES`.

Per registrar candidata:

1. rol manage;
2. `SIF_RUNTIME_GIT_REVISION` vàlid;
3. manifest privat disponible;
4. tots els bytes del manifest concordants;
5. ledger de migracions íntegre i esquema complet.

Per activar:

1. tot l'anterior;
2. candidata DRAFT existent;
3. declaració `APPROVED` amb bytes físics verificats;
4. `SIF_VERSION_ACTIVATION_ENABLED=1`;
5. evidència UC-85 acceptable si `SIF_VERSION_REQUIRE_BACKUP_EVIDENCE=1`;
6. cap inconsistència de singleton/ACTIVE;
7. candidata igual al runtime observat **en aquell moment**.

## 5. Entrades

### 5.1. Registrar candidata

Client:

- `version_code`;
- `request_id`;
- `correlation_id`;
- `idempotency_key`;
- `reason_code`.

Servidor:

- `GIT_REVISION`;
- `ARTIFACT_HASH`;
- `CONFIG_HASH`;
- `DATABASE_VERSION`.

Els quatre valors server-authoritative **no són inputs del navegador**.

### 5.2. Vincular declaració

- `uuid_version`;
- `declaration_version`;
- `storage_key` relatiu al root privat;
- ids operacionals i motiu.

`APPROVED_BY`, `APPROVED_AT` i `DOCUMENT_HASH` es deriven al servidor.

### 5.3. Activar

- `uuid_version`;
- `backup_evidence_uuid` quan correspongui;
- ids operacionals i motiu.

## 6. Sortides

### Consulta runtime

- entorn;
- Git revision;
- artifact hash;
- config hash;
- database version;
- `schema_verified`;
- resum del manifest;
- errors de verificació sense secrets.

### Candidata

Fila `sif_version` amb estat DRAFT.

### Declaració

Fila `sif_declaration` amb estat explícit APPROVED.

### Activació

- actualització del singleton `sif_version_state`;
- estat ACTIVE de la candidata;
- SUPERSEDED de l'anterior;
- fila immutable `sif_version_activation`;
- `sif_audit_event`;
- `operational_event`.

## 7. Regles de negoci

### UC010-R01 · Un sol writer

`SifVersionService` és el writer canònic de versions/declaracions/activacions. UC-46 i UC-83 han de reutilitzar aquest contracte.

### UC010-R02 · Git no acredita el runtime

Una revision Git registrada no és suficient. Els bytes del manifest s'han de tornar a verificar.

### UC010-R03 · No acceptar hashes de client

Els hashes/versió BD de candidata només provenen de `RuntimeVersionInspector`.

### UC010-R04 · Config hash

Es calcula canònicament sobre la configuració carregada en memòria. No es persisteix ni retorna la configuració sencera. S'exclouen `runtime_git_revision`, `release_manifest_path` i `activation_enabled`: Git/artefacte tenen identitat pròpia i el gate operatiu es pot habilitar després de registrar una candidata sense provocar un fals drift.

### UC010-R05 · Declaració física

`STORAGE_KEY` sense fitxer no és evidència. El fitxer ha d'estar sota root privat i el SHA-256 ha de concordar en preflight.

### UC010-R06 · Activació no és desplegament

UC-010 no fa FTP, checkout, rsync, restart ni rollback físic. Només registra una versió que **ja coincideix** amb el runtime.

### UC010-R07 · Exclusivitat ACTIVE

L'activació obté `FOR UPDATE` sobre `sif_version_state(ID=1)` i sobre les files ACTIVE. Múltiples ACTIVE o un pointer incoherent bloquegen.

### UC010-R08 · Preflight revalidat sota lock

Abans d'escriure ACTIVE es torna a inspeccionar el runtime.

### UC010-R09 · Idempotència

Mateixa key + mateix payload → reutilització.  
Mateixa key + payload diferent → 409.

### UC010-R10 · No mutació fiscal retroactiva

Canviar versió/configuració no modifica factures, numeració, hash chain, pagaments, callbacks ni registres AEAT ja existents.

### UC010-R11 · Fail-closed

- rols buits → denegat;
- activation flag absent/0 → NO-GO;
- manifest absent → runtime incomplet;
- declaració absent → NO-GO;
- backup obligatori absent/no íntegre → NO-GO.

## 8. Flux principal A — registrar candidata

1. Usuari obre el panell des de la intranet.
2. HMAC launch valida actor/rol/path/request i crea sessió.
3. Usuari introdueix només `VERSION_CODE`.
4. Backend inspecciona runtime.
5. Manifest verifier recalcula hashes dels fitxers.
6. Config fingerprint calcula hash efectiu.
7. MigrationRunner verifica ledger i esquema.
8. Si tot és complet, INSERT DRAFT idempotent.
9. Es registra audit/operational event.
10. UI refresca la candidata.

## 9. Flux principal B — declaració

1. Usuari selecciona candidata.
2. Informa versió documental + `STORAGE_KEY`.
3. Backend resol el fitxer dins del root privat.
4. Rebutja traversal/symlink fora de root/fitxer absent.
5. Calcula `DOCUMENT_HASH`.
6. Registra l'actor autenticat com aprovador.
7. INSERT APPROVED idempotent.
8. Registra auditoria.

## 10. Flux principal C — preflight

Comprova:

1. activation flag;
2. runtime complet;
3. Git;
4. artifact hash;
5. config hash;
6. database version;
7. schema;
8. declaració;
9. bytes/hash declaració;
10. backup evidence quan correspongui.

Retorna `failed[]` explícit.

## 11. Flux principal D — activació

1. Comprovar replay idempotent.
2. Executar preflight.
3. BEGIN.
4. Lock candidata.
5. Lock singleton.
6. Lock ACTIVE rows.
7. Validar coherència.
8. Reexecutar preflight sota lock.
9. Marcar anterior SUPERSEDED.
10. Marcar candidata ACTIVE.
11. Actualitzar singleton.
12. Append activation journal.
13. Append audit + operational event.
14. COMMIT.

## 13. Persistència

### `sif_version`

Identitat immutable de candidata + evidència observada.

### `sif_declaration`

Metadades d'aprovació + hash dels bytes.

### `sif_version_state`

Singleton de coordinació, no historial.

### `sif_version_activation`

Journal immutable i principal evidència d'activació.

### `backup_restore_evidence`

Font UC-85; UC-010 només llegeix.

### `sif_audit_event` / `operational_event`

Traça transversal.

## 15. Impacte fiscal/econòmic

La pròpia operació UC-010 registra:

- `FISCAL_IMPACT=NONE`;
- `ECONOMIC_IMPACT=NONE`.

Això no significa que una nova versió no pugui canviar comportament fiscal futur; significa que **l'acte de registrar/activar versió no crea un fet fiscal ni econòmic**.
